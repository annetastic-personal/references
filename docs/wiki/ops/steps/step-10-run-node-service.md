# Step 10: Run a Node Service (systemd)

> **Applies to:** Node service deployments (PERN, MERN).

Worked example: [Step 10 Sample](https://github.com/annetastic-personal/references/wiki/step-10-run-node-service-sample)

## Purpose

A Node.js backend is a long-running program, not a folder of files — it only
serves requests while the process is actually running. A process started in a
terminal stops when you log out or when the server reboots, and nothing
restarts it if it crashes.

This step installs a systemd unit so the operating system manages the Node
process for you: it starts the service on boot, restarts it automatically after
a crash, and gives you one place to check status and logs. No half-remembered
terminal session required.

---

## 1. Create a systemd unit

Create `/etc/systemd/system/<service-name>.service`:

```ini
[Unit]
Description=<service-name> Node.js service
After=network.target

[Service]
Type=simple
User=<deploy-user>
Group=<deploy-user>
WorkingDirectory=/var/www/<project>/current
ExecStart=/usr/bin/node <entry-point>
Restart=on-failure
RestartSec=5
Environment=NODE_ENV=production
EnvironmentFile=/var/www/<project>/shared/.env

[Install]
WantedBy=multi-user.target
```

> **Runs on:** the server — SSH in first, then create the file at the remote prompt.

The four placeholders, in the order they appear in the file:

- **`<service-name>`** — the short name you chose for this process in Step 7
  (for example `ttgcollector`). It becomes the unit filename
  (`<service-name>.service`) and the name you pass to `systemctl` below. Use the
  exact string from the Step 7 restart line.
- **`<deploy-user>`** — the Linux account the service runs as (the deploy user
  from Steps 1–2, for example `debian`). `User=` and `Group=` run the process as
  this user instead of `root`.
- **`<project>`** — the folder name under `/var/www` (for example `ttgcollector`),
  the same `<project>` used in Steps 2 and 7.
- **`<entry-point>`** — the path to the JavaScript file that starts the server,
  relative to `WorkingDirectory` (for example `server/server.js`). This is the
  file your `npm start` script runs.

Reading the file top to bottom:

- `After=network.target` starts the service only after the network is up. If the
  app uses a database, list its service here too (for example
  `After=network.target postgresql.service`) so the database is up first.
- `WorkingDirectory` runs the process from the `current` symlink. Each deploy
  repoints `current` to a new release directory (Step 11) and restarts the
  service, so you do not edit this file on every deploy.
- `ExecStart=/usr/bin/node <entry-point>` launches the server with the
  system-wide Node installed in Step 8.
- `Restart=on-failure` and `RestartSec=5` restart the process automatically if
  it crashes.
- `Environment=NODE_ENV=production` sets that one variable inline.
- `EnvironmentFile=/var/www/<project>/shared/.env` loads the app's runtime
  configuration and secrets — the file you created in Step 9.
- `WantedBy=multi-user.target` (under `[Install]`) makes the service start on
  boot.

## 2. Enable the service (start on boot)

```bash
sudo systemctl daemon-reload
sudo systemctl enable <service-name>
```

> **Runs on:** the server — SSH in first, then run at the remote prompt.

This registers the service to start on boot, but does not start it now — there
is no code to run yet. Step 9 created the database and `.env`, but the `current`
symlink still points at the empty `releases/initial/` from Step 2, so there is
nothing for the service to start. The first actual start happens during the
Step 11 deploy, which restarts the service after copying the code.

## 3. Confirm the service is registered

```bash
sudo systemctl is-enabled <service-name>
```

> **Runs on:** the server — SSH in first, then run at the remote prompt.

Expected: `enabled`. This confirms the unit file is valid and registered to
start on boot. `systemctl status <service-name>` still reports
`inactive (dead)` at this point — that is expected, because the service has not
been started yet. The first start happens during the Step 11 deploy.

To validate the unit file itself, run:

```bash
sudo systemd-analyze verify /etc/systemd/system/<service-name>.service
```

> **Runs on:** the server — SSH in first, then run at the remote prompt.

No output means the unit is syntactically valid.
